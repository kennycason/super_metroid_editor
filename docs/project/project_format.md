# Native SMEDIT Project Format

`.smedit` is SMEDIT's native JSON project format. It is not another editor's project file and it
does not embed another editor's configuration model.

## What A Project Stores

A project identifies its immutable base ROM with a project-relative `romPath` and stores semantic edits applied by
SMEDIT at export time. By default that file is the immutable build base. An opted-in
Project ASM workspace may instead select a clean source compilation as the build base;
the loaded ROM remains the private asset source and comparison input. The current top-level model includes room edits, room-state manifests,
tileset defaults, patches, custom graphics, patterns, minimap and map-station edits, text and room
name overrides, custom ASM, music edits, project UI settings, and ROM build-label fields.

`customGfx.samusCommunitySource` is an optional project-owned SpriteSomething/MapRando
Samus source. It embeds the original PNG with its layout ID, SHA-256, attribution, and
catalog provenance so the project does not depend on a machine-local download cache.
A compatible catalog selection also embeds a versioned injection artifact containing
the pinned Map Randomizer IPS, both source and artifact hashes, provider revision,
exact base-ROM identity, and 3 MiB → 4 MiB size contract. Local/private PNGs have no
artifact and are explicitly source-only; ROM validation blocks those rather than
silently omitting them. Removing `samusCommunitySource` is the complete "Restore Base
ROM Samus" operation: export always rebuilds from the immutable ROM at `romPath`.

`generalSettings` contains project-local editor preferences that should follow the project rather
than the machine. Its `patchBrowser` section stores alphabetical sort direction and whether
favorites are grouped first. Patch favorite IDs are application-wide and are written immediately
to SMEDIT's global config; the project field remains only as a migration source for files written
by older builds. Patch search text is intentionally session-only and is not saved. Enabled patches
are always grouped above disabled patches; favorites and alphabetical sorting apply within those
groups. These settings affect presentation only and never change ROM export behavior.

`asmWorkspace` is the portable contract for the project-owned ASM sidecar. `enabled`
and `sourceRevision` identify the pinned source snapshot, while `buildMode` is either
`PATCHED_ROM` (the default shown as **Loaded ROM**) or
`ASM_SOURCE`. Enabling Project ASM selects `ASM_SOURCE` automatically. A clean ASM
workspace may return to `PATCHED_ROM`, but saved or unsaved source edits require
`ASM_SOURCE`; both the UI and export validation prevent those edits from being
silently ignored. Authored source lives under `asm/`; generated source/data trees live
under `smedit/asm/`. They are not embedded in JSON. Saved source overrides
are the portable authored content. In `ASM_SOURCE` mode the two source trees compile
before the shared semantic-edit and patch transaction, and their authored byte delta
becomes a normal conflict-checked ROM owner. Eligible fixed-range editor writes are
projected into temporary copies of exact manifest-owned `data/` assets before the
second compilation; those generated bytes are separately conflict-checked and never
rewrite the workspace. Ambiguous, inline, and allocated edits keep the established
post-compile path, and final ROM parity with that path is mandatory.
Patch backend support is an application capability rather than duplicated project
state: a patch stores one semantic configuration, and the selected ROM build mode
chooses its registered implementation. Patches without ASM support safely retain
their post-compile ROM writer. GUI-generated ASM modules are temporary build inputs
and are neither embedded in JSON nor written into `overrides/src/`.
Here, `data/*.bin` means an extracted source asset consumed by the disassembly;
it is distinct from an IPS or fixed-offset ROM-byte patch applied after compilation.

`asmWorkspace.enemyTuningSourceKeys` records owned enemy HP/contact-damage/drop/vulnerability
field identities, never their values or compiled addresses. First edits retire the
corresponding legacy patch-config keys in the same source/model undo transaction.
Authored values stay in the native bank source; builds validate header identities,
symbolic drop pointers and byte ownership. ROM-only builds cannot ignore these keys.
`asmWorkspace.beamDamageSourceKeys` likewise stores normal/charged beam word identities
(`power`, `power_charged`, etc.), with values only in native bank-93 source. A legacy
normal-only patch still implies 3× charged damage; adoption preserves the untouched
half in source and retires its implicit override atomically. New explicit charged
keys are independent in desktop and headless ROM patches. ASM builds validate live
symbolic pointer bindings and resolve legacy patch destinations from compiler symbols,
never fixed native damage offsets. Headless builds cannot omit authored tuning source.
`asmWorkspace.bossStatsSourceKeys` stores boss HP/contact-damage identities, with
values only in native bank-A0 source. A grouped control owns every configured
sub-species word, including unchanged bytes. Independent sub-species values remain
authorable in ASM and make only that grouped GUI control read-only. Mixed enemy/boss
text edits retire their config keys and restore them on Undo as one transaction.
Both build modes end in a binary ROM—the ASM choice changes the order and ownership
of inputs, not the output format.

## Project Root And Opening Workflow

The `.smedit` file is the entry point, not a sidecar inferred from a renamed ROM.
One project lives in each directory. `ProjectPaths` is the shared path contract:

```text
Super Metroid ASM Sandbox/
  Super Metroid ASM Sandbox.smedit
  Super Metroid [JU].smc              # immutable supplied base; original filename
  Super Metroid ASM Sandbox-v1.0.smc  # generated build; project name + version
  asm/
    modules/                         # authored modules, .order and .disabled
    overrides/src/                   # authored replacements for source banks
  data/                              # reserved for explicit custom asset inputs
  states/                            # emulator SRAM and save states
  exports/graphics/                  # generated CRE/URE preview PNGs
  smedit/asm/
    original/                        # pinned source + private extracted assets
    workspace/                       # generated editable mirror
    build/                           # compiler reports, symbols, generated rooms
    .smedit-project-asm.properties
```

Project-local support folders are simply `smedit/` and `states/`; the parent folder
already identifies the project. The application-wide `~/.smedit/` directory is
separate and keeps its existing name.

Directories are created only when used. `data/` is a reserved location, not a new
automatic import mechanism: custom graphics, community Samus sources and music
edits remain authoritative in the project JSON. Generated PNGs are previews, not
editable build inputs. Other manually chosen export destinations remain user-controlled.
An authored module is never recovered from a stale generated mirror.

- **NEW** asks for name, parent folder and base ROM. It creates a new project folder,
  copies the ROM without renaming it, and starts in ROM-patching mode. Existing folders
  and files are never overwritten by project creation. ASM can be enabled afterward;
  it still needs that private ROM for extracted assets.
- **OPEN** accepts `.smedit`, `.smc` or `.sfc`. A project opens its recorded base. A ROM
  beside exactly one project opens that project, including when the selected ROM is
  a generated build. A standalone editable ROM opens the prefilled NEW dialog; compatible
  inspection-only ROMs still open read-only. Multiple neighboring projects require an
  explicit project-file selection. Discovery is not recursive.
- **Missing/mismatched base** opens Locate base ROM, naming the original file. New
  projects record `baseRom.originalFileName`, headerless `sha256` and `size`. A renamed
  or copier-headered copy is accepted if its contents match; a different revision,
  hack or modified build is refused. The selected copy is imported into the project
  root, with no overwrite of an existing differently located file. Projects without
  identity metadata explicitly warn that this first choice establishes the identity.
- Saves write a relative ROM filename atomically. Runtime code resolves it against
  the project directory. Copying/moving the entire directory does not require editing
  absolute machine paths. The loader never substitutes an empty project for corrupt JSON.
- `projectId` is generated for a new project and persists across moves. Last-room
  preferences are keyed by this ID, not the shared base-ROM filename. The application
  remembers the last `.smedit` file, so missing-ROM recovery also works on startup.
- Exports use the **project** name, build label and version, not the base-ROM name.
  Output paths reject unsafe names and any destination that would replace the input ROM.

Source control should include `.smedit`, `asm/modules/`, `asm/overrides/`, and genuinely
authored assets. Do not commit ROMs, extracted binary assets, `smedit/`, `states/`
or generated previews. NEW writes a local `.gitignore`. Changing ignore rules does not
untrack ROMs already committed to the repository; cleaning those up is a separate step.

### Migrating Existing Local Projects

The editor deliberately has no automatic legacy-folder migration or dual-layout fallback.
For a one-off migration, close SMEDIT and use the standalone Bash script (Python 3.8+
required; standard library only):

```bash
# Preview only: no files are changed or backups created.
./tools/migrate_project.sh '/path/My Project/Old Name.smedit'

# Back up and apply the migration.
./tools/migrate_project.sh --apply '/path/My Project/Old Name.smedit'
```

Select the authoritative root project, not a historical nested copy. The script renames
the selected file to match its containing folder (`My Project/My Project.smedit`); the
folder and base ROM keep their names. It moves legacy support folders, separates authored
ASM from generated caches, archives nested historical projects, and records a relative
base-ROM filename and stable project ID without changing gameplay data or schema markers.
Unknown JSON fields are preserved, though updated JSON is serialized compactly.

An existing root base ROM is fingerprinted (ignoring a copier header); a recorded fingerprint
mismatch aborts. Without a fingerprint, review the preview's ROM filename before proceeding.
If the base is missing, the script does not guess or copy another ROM: **OPEN** will request
Locate base ROM. Existing identity metadata is retained. Root `.gitignore` rules are extended
without removing custom rules; this does not untrack files already committed.

Applying makes a complete, verified private backup under `~/.smedit/backups/` and verifies
file contents again after moving. Use `--backup-dir '/path/to/backups'` to choose another
backup parent outside the project. Do not publish these backups: they may include ROMs and
extracted assets. Conflicting old/new destinations, multiple root project files, symlinks,
and malformed JSON are refused rather than merged or overwritten. A completed migration
can be rerun using the new project filename. On an interrupted/failed migration, keep both
copies and recover from the printed backup before opening/building the project.

The script covers these paths; they can also be moved manually after backing up:

| Existing content | New location relative to the project root |
|---|---|
| Authoritative top-level `.smedit` | Keep at the root |
| Original input ROM | Root, ideally its original filename |
| `<name>_smedit/asm/modules/` and `overrides/` | `asm/modules/` and `asm/overrides/` |
| `<name>_smedit/asm/original/`, `workspace/`, `build/` and ASM metadata | `smedit/asm/` (or rebuild these caches) |
| `<name>_states/` or `emu_states/` | `states/` |
| Project-local `.smedit/` from the earlier layout | `smedit/` |
| Generated CRE/URE PNGs, mapshots, MIDI/SPC exports | `exports/` (graphics previews go under `graphics/`) |
| Hand-edited assets | Preserve separately, optionally under `data/`; do not confuse with generated previews |
| Nested historical `.smedit` files | Preserve/archive; never silently merge or discard |

Open the root project and locate the base if its recorded path changed. Saving records
the relative filename and fingerprint. If the generated ASM cache was not moved, use
ASM's Download/Refresh as needed, then **Repair Project ASM** to recreate it from the
pinned reference plus `asm/` authored inputs. Move authored source **before** repair/build.
The repository's local `projects/` directories were reorganized separately on 2026-10-12,
after a full backup and with file-content verification. Spike Olympics' older nested project
contains distinct historical edits and is preserved in `archive/legacy-project/`; its loose
tileset images are in `data/legacy-assets/`. The editor itself does not automatically move or
delete legacy folders.

The migration regression tests use temporary synthetic projects only:
`python3 -m unittest discover -s tools/tests -v`.

Room data is described in [`room_model.md`](room_model.md). `newRooms` owns stable project room
identities, complete initial headers/default-state payloads, and semantic door destinations.
Top-level room operations, PLM changes,
enemy changes, and similar lists are common edits applied across that room's states. The equivalent
lists inside `RoomStateEdits` target one state for non-layout data.
`RoomEdits.levelResourceOperations` stores tile, BTS, and embedded Layer 2 operations once per
complete semantic layout identity, whether that identity is shared by several states or unique to
one. A state cannot own a partial tile overlay: making it independent creates a new whole-layout
identity. PLMs, enemies, effects, and scroll metadata remain state-owned even when they were placed
by the same canvas action. Legacy beta state tile overlays are promoted to unique complete layouts
on load. All are parts of the same current room model.

ROM addresses and allocation choices are export results, not the long-term identity of newly
authored data. Existing rooms remain keyed by their source room-header ID. Project-owned rooms use
IDs such as `room-1`; their `previewRoomId` is a rebuildable workspace adapter and is never used to
resolve exported doors or treated as persistent identity.

## Project Format and Versioning

There is one development format, identified by an explicit envelope:

```json
{"projectFormat":"smedit-project","projectFormatVersion":1,"projectId":"stable-project-id","romPath":"Base.smc"}
```

The 2026-10-16 baseline consolidates the experimental numbered beta formats. Both
desktop and CLI use the same strict codec. Missing/wrong format markers, unsupported
versions, unknown fields, invalid enums and missing/blank identities are errors;
opening a project never silently migrates, drops or coerces authoring data. Optional
domain values still have ordinary defaults. New projects receive an identity once,
and saved identities survive moving/renaming a project folder.

Version 1 includes all current room/resource ownership, structural doors, symbolic
incoming-door conditions, assets, patches and project settings. The version is not
a feature counter: compatible optional additions use defaults; incompatible saved
contracts require an intentional version change and an explicit update of our
development projects. We do not maintain parallel historical model implementations.
Pre-baseline builds are unsupported for normalized projects; do not round-trip these
files through an old editor, which cannot understand the new format identity.

`versionMajor`, `versionMinor` and `buildName` label exported ROM/IPS filenames. They
are independent of the project format. Room capability markers such as
`asmDoorSourceVersion` and `asmLayoutSourceVersion` are also independent: 0 means
GUI/ROM ownership and 1 means the supported authored source contract. They retain
their ownership checks. JSON stores identities/ownership, not duplicate source
values, compiled addresses or transient GUI projections. See the
[source ownership contract](../asm/reference_workspace.md#reciprocal-sourcegui-ownership--first-authoring-slice),
[structural doors](../asm/reference_workspace.md#structural-door-lists) and
[symbolic conditions](../asm/reference_workspace.md#symbolic-incoming-door-conditions).

### Explicit Offline Normalization

Close SMEDIT before rewriting project files. These commands preview, apply, or
verify the active projects (one `.smedit` per immediate child folder):

```bash
./gradlew :cli:normalizeProjects
./gradlew :cli:normalizeProjects -Pargs='--apply projects'
./gradlew :cli:normalizeProjects -Pargs='--check projects'
```

The offline tool validates every input first, fills current serialized defaults,
preserves every existing authored value/list/identity, verifies idempotent strict
round trips, and refuses unknown fields or future formats. Applying writes creates
verified recovery copies in a printed temporary directory and atomically replaces
each unchanged input. It does not modify ROMs, ASM, assets, historical archives or
existing backups. Explicit `.smedit` file paths may also be supplied. Ordinary
Open/Save never invokes this tool and no longer generates schema-upgrade sidecars.

## ROM Compatibility Is Separate

Project format, ROM layout, and room-state predicate bytecode are independent concerns:

- The project schema controls how `.smedit` JSON is serialized.
- The ROM compatibility layer decides whether a selected ROM can be edited or only inspected.
- SMEDIT's tagged room-state predicate formats are generated ROM code/data ABIs. Their version
  bytes do not describe the `.smedit` schema.

The ordinary editable path targets the standard 3 MiB Super Metroid ROM layout. A verified
community Samus artifact is the narrow exception: it requires the exact clean base and produces a
known 4 MiB output inside the normal transactional exporter. Other expanded or relocated ROMs can
be inspected read-only when discovery succeeds; their discovered catalogs are derived from ROM
bytes in memory and are not copied into the project as foreign-editor metadata.

## Foreign-Format Imports

Any future foreign-editor import must be a one-way translation boundary:

1. Parse the foreign file into a temporary importer model.
2. Validate every supported concept and report anything that cannot be represented safely.
3. Translate supported data into the native SMEDIT model.
4. Save only native `.smedit` data; do not retain a foreign XML blob or add a second internal save
   path.

SMILE normally edits ROM bytes rather than producing a separate project format. Opening a ROM that
was previously edited by SMILE is therefore ROM compatibility, not SMILE-project import.
